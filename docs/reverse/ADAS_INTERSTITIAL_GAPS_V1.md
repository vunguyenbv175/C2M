# ADAS Interstitial Gaps V1 — EN vs VI

**Scope:** the seven non-model regions inside the self-contained stock `adas` executable.  
**Ground truth:** EN 2023-08-03 is known-good on the user's C2M; VI 2023-09-20 did not provide working ADAS on the same unit.

## Executive result

The six embedded CNN/model blobs are byte-identical EN vs VI. Every byte of the VI file-size growth is therefore outside those six models.

Exact geometry:

| Gap | EN bytes | VI bytes | VI - EN |
|---|---:|---:|---:|
| ELF end -> `d0` | 7,394 | 8,706 | +1,312 |
| `d0` -> `v_a` | 16,790 | 21,304 | +4,514 |
| `v_a` -> `v_t` | 7,624 | 16,974 | +9,350 |
| `v_t` -> `p_r` | 17,384 | 15,410 | -1,974 |
| `p_r` -> `road` | 14,532 | 15,616 | +1,084 |
| `road` -> `tl` | 20,660 | 21,880 | +1,220 |
| `tl` -> packaged flags | 6,746 | 9,102 | +2,356 |
| **Total delta** |  |  | **+17,862** |

The sum of the seven gap deltas is exactly the whole-file delta:

```text
VI file size - EN file size = +17,862 bytes
sum(gap deltas)           = +17,862 bytes
```

Therefore:

> **CONFIRMED:** no part of VI's size increase is caused by larger CNN/model blobs.

## What the gaps look like

Previous direct binary inspection found all seven regions to be high-entropy (roughly 7.97–7.99 bits/byte) with no useful plaintext header commonality and no obvious repeated 16/32-byte block structure.

That observation is now made reproducible by:

```text
tools/fw/adas_gap_report.py
```

The tool calculates per gap:

- start/end/size,
- SHA-256,
- Shannon entropy,
- printable-ASCII ratio,
- zero-byte ratio,
- 16-byte and 32-byte block repetition,
- EN/VI common prefix and suffix,
- aligned equal-byte ratio,
- 16-byte block-set Jaccard similarity.

This is deliberately format-agnostic. It does not label the regions as encrypted/license/protection data until the consumer code is proven.

## Why this matters for the VI regression

The static evidence now excludes or weakens several simple explanations:

### Strongly reduced

```text
VI shipped different CNN weights
VI changed CNN model sizes
VI m0 points to stale model offsets
broad ADAS algorithm rewrite
SystemInit removed the IPU creation path
```

### Remaining high-value suspects

1. **Protected/interstitial package metadata** changed between EN and VI.
2. **Validation/decryption/licensing code** interprets that metadata differently at runtime.
3. A small same-size code/data change inside `adas` remains possible.
4. **`cardv` / `raw_adas` producer integration** remains a separate high-priority suspect.
5. Kernel/driver/memory-layout changes remain possible if VI `adas` works on an EN base.

## Critical runtime discriminator

The most valuable safe experiment is still:

```text
EN working kernel/rootfs/cardv/config
+
VI adas executable only
```

Run it from a temporary path without replacing the golden binary.

Interpretation:

```text
VI adas fails on EN base
  => defect is inside VI adas package or its interpretation of persistent config/license/calibration

VI adas works on EN base
  => shift focus to VI cardv / raw_adas / kernel / module integration
```

The goal is to identify which function reads or validates bytes from the seven gaps.

If no executable code ever consumes those gaps except the model loader/protection wrapper, they are likely packaging/protection material rather than ADAS algorithm data.

## Reproduction

After extracting EN/VI `adas` binaries:

```sh
python3 tools/fw/adas_gap_report.py \
  <EN-adas> <VI-adas> \
  --left-model-txt <EN>/params/model.txt \
  --right-model-txt <VI>/params/model.txt \
  -o gaps.json \
  --markdown gaps.md
```

`cryptography` is needed only when the tool decrypts `m0` itself. It can alternatively consume model-directory JSON generated by `adas_m0_directory.py`.

Static geometry used in this document is also stored in:

```text
docs/reverse/EVIDENCE_ADAS_GAP_GEOMETRY.json
```
